# CLAUDE.md

CloudStore stores a nested cloud hierarchy (management groups, subscriptions, resource groups) in
Postgres and serves it over HTTP. `POST /hierarchy` saves a hierarchy as an upsert — re-submitting a
changed hierarchy must handle added, removed, and moved nodes. `GET /hierarchy/{node_id}` returns
that node with all of its descendants nested underneath.

**This project implements the Python server** (`python-server/`, port 8081) on FastAPI, SQLAlchemy
2.0, Alembic and psycopg 3, async end to end. The Go server is left as the reference stub it shipped
as — don't build features there. `README.md` is this project's front page; `exercise.md` is the
original assignment brief, kept verbatim as the record of what was asked for — don't edit it.

## Rules

- **Ask before assuming**: When a task is ambiguous, requirements are unclear, or you're unsure about the intended approach, ask clarifying questions before proceeding. Don't guess — it's better to ask than to build the wrong thing.
- **Don't write code unless asked**: Default to investigation and explanation only. Do not write, edit, or commit code unless the user explicitly asks you to. Answer questions, diagnose issues, and propose solutions verbally first.
- **Write tests for code changes**: When you change or add code, add or update tests that cover the new behavior. New tests go in `python-server/tests/`; never delete or weaken anything in `tests/` — `run_tests.py` and `objects/*` are the assignment's, and it forbids that. This project has **no CI pipeline** — nothing runs your tests but you — so bring the stack up with `docker compose up --build -d`, run **both** suites locally before opening a PR, and paste both results in the PR description:
  - `uv run pytest` from `python-server/`, with `DATABASE_URL=postgresql://aryon:aryon@localhost:5432/aryondb` in the environment. `uv` resolves the locked dependency set itself — there is no `requirements.txt` and no virtualenv to activate. Without a reachable Postgres the database tests skip rather than fail, so read the skip count as carefully as the pass count.
  - `uv run --no-project --with-requirements tests/requirements.txt python tests/run_tests.py` from the repo root (it resolves `tests/objects` relative to the working directory). On Windows prefix `PYTHONIOENCODING=utf-8`, or its ✅ output dies on cp1252. It has to report 6/6 and exit 0.
- **Avoid default values**: Try to avoid giving variables and parameters default values unless a default is specifically needed. Prefer making callers pass values explicitly so intent is clear and missing values surface as errors instead of being silently filled in.
- **Environment variables**: Never read environment variables (`os.getenv`, `os.environ`, etc.) outside of a single central config module in `python-server/`. That module is `python-server/app/config.py`: it reads and validates `DATABASE_URL` with no fallback, so a missing or malformed value is a startup failure rather than a request-time 500. Import `settings` from it everywhere else — no other module should touch the environment.
- **Layering**: `python-server/app/` splits in two. `app/api/` is the HTTP layer — `routes/`, HTTP-only response schemas in `schemas/`, the exception-to-status mapping in `errors.py`, and app assembly in `main.py`; it is the only place FastAPI is imported. `app/lib/` is the reusable layer — domain types in `types/`, the `HierarchyService` use cases in `hierarchy.py`, SQLAlchemy tables in `models/`, storage in `repositories/`, and the engine in `database.py`. **`app/lib/` must never import from `app/api/`.** That one-way dependency is the whole point: it is what lets a second front end (a CLI, a worker, another API) call `HierarchyService.store_hierarchy` without dragging FastAPI along. `app/config.py` sits above both. Note `models/` means SQLAlchemy and `schemas/` means Pydantic, per FastAPI convention.
- **Repositories**: `repositories/base.py` declares `HierarchyRepository`, the abstract storage interface the use cases are written against; `repositories/postgres_hierarchy.py` is the one implementation. The interface speaks ids and the `NamedTuple`s in `types/rows.py` — never an `AsyncSession`, a SQLAlchemy `Row`, or anything else driver-specific — and `hierarchy.py` and `base.py` import no SQLAlchemy at all. A repository instance is one unit of work and owns its own transaction, so `commit()` is on the interface rather than something a caller reaches around it for. **The route is the composition root**: `build_service` in `app/api/routes/hierarchy.py` is the only place that names `PostgresHierarchyRepository`. Keep it that way — picking the implementation is the decision `app/lib/` deliberately does not make, and it is what leaves that layer reusable.
- **Database schema**: **Alembic owns the schema.** Every change is a new revision in `python-server/alembic/versions/`; `postgres/init.sql` is deliberately empty and stays that way. Never create or alter a table by hand against a running database — the next person to start fresh would get a different schema than you have. The API container runs `alembic upgrade head` before uvicorn, so `docker compose up --build -d` applies whatever is pending and a failed migration stops the container rather than serving against a schema the code does not match. Generate and inspect revisions in the container (`docker compose exec python-server uv run alembic revision --autogenerate -m "..."`) — on the host they work on Linux and macOS but not on Windows, where `alembic/env.py`'s `asyncio.run` builds the `ProactorEventLoop` psycopg refuses. Autogenerate only sees models reachable from `alembic/env.py`, so add every new model module to the import line there, and always read what it wrote: it handles the native `node_type` enum badly, which is why revision `0001` is hand-written. Both `upgrade` and `downgrade` must be correct: `downgrade base` followed by `upgrade head` has to succeed, which is what `python-server/tests/test_migrations.py` checks by asserting on the DDL each direction emits (`alembic upgrade head --sql`, no database needed).
- **Workflow**: At the start of a task, pull the latest `dev`. Branch from `dev`, and when the work is done open a PR into `dev` — then **stop**. Do NOT merge it: the user reviews and merges every PR manually. Resolve any merge conflicts with `dev` before handing the PR over, and say plainly in the PR description what you ran and what passed. After the user merges, sync your local `dev` with the remote in the **main project directory** (where `dev` is checked out), not in a worktree — git won't update a branch checked out elsewhere.
- **Releasing to `main`**: Merging `dev` → `main` is a release. Always ask the user for explicit confirmation before opening a `dev` → `main` PR, run the full test suite locally first, and leave the merge itself to the user.

## Tools

- **Docker Compose** — the whole stack. `docker compose up --build -d` starts Postgres (5432), the FastAPI server (8081), and the Go stub (8080), migrating the database before uvicorn starts. `docker compose logs -f python-server` for server logs; `docker compose down -v` to drop the stored data and start clean.
- **uv** — the dependency manager for `python-server/`, driven by `pyproject.toml` and the committed `uv.lock`. `uv run <cmd>` from `python-server/`; `uv add`/`uv remove` to change dependencies, and commit the updated lock file. Never `pip install`, and never edit a lock file by hand.
- **Test suites** — two, and both are described under the testing rule above: `uv run pytest` from `python-server/` for our own tests, and `tests/run_tests.py` from the repo root for the assignment's six fixtures, which it stores and fetches back to compare the JSON.
- **psql** — inspect the database directly with `docker compose exec postgres psql -U aryon -d aryondb`. The pytest suite uses a separate `aryondb_test` database, so it never touches what the fixture suite stored.
- No MCP servers are configured for this project, and there is no hosted database — Postgres runs locally in Docker.
